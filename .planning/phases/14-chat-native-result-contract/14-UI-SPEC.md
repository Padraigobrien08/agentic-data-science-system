## Visual Hierarchy

**Primary focal point:** the latest assistant answer card. The user should land on the conclusion first, not on run links, technical metadata, or transcript chrome.

**Reading order:**
1. Latest pending or completed assistant answer card
2. Compact run identity strip attached to that answer
3. The user prompt that produced the answer
4. Prior prompt/answer pairs in transcript order
5. Composer and scope editor

**Layout rules:**
- Keep one primary transcript column. The sidebar stays secondary navigation, not a competing content region.
- The assistant answer card must feel like a compact analysis surface, not a generic bubble with utility links.
- The conclusion block is the first readable content inside the assistant card; goal and technical disclosure sit below it.
- The run identity strip is supportive metadata at the bottom of the card, never the visual anchor.
- Pending and terminal answer cards should preserve the same footprint so in-place replacement does not shift the transcript abruptly.

**Icon-only controls:**
- Avoid icon-only controls in the transcript and composer for this phase.
- If an icon-only affordance is unavoidable, it must include an `aria-label`, tooltip, and a nearby text equivalent on narrow screens.

| 3xl | 64px | Page-level vertical spacing only |

## Component Contract

| Surface | Contract |
|---------|----------|
| Transcript shell | One workspace-level visible conversation. Oldest messages render at the top, newest at the bottom. Do not present client-only local sessions as durable history. |
| User bubble | Keep the existing right-aligned bubble pattern at max width `36rem`; no redesign in this phase. |
| Assistant answer card | Left-aligned structured card at max width `42rem`. Render only the compact summary layer: conclusion, goal, optional conclusion rider, optional technical-status disclosure, and the run identity strip. |
| Pending assistant slot | Reuse the final answer-card footprint while pending. Show a muted or skeleton state with `Running analysis...` plus `Updating…`; do not append a second completion bubble later. |
| Unsupported guidance reply | Keep the current inline rewrite-guidance block for unsupported routing. No run strip, no `Open run` CTA, no run metadata. |
| Run identity strip | Bottom row inside the assistant answer card with friendly status badge, one locale-formatted timestamp, short monospace run id, and one primary `Open run` action. No `Deep dive` or `All runs` links in Phase 14. |

## Interaction Contract

- Hydrate chat history from persisted project runs, not from local-only session stubs. The visible transcript is reload-safe because persisted runs are the source of truth.
- Map each persisted run into exactly two transcript rows: one user prompt row and one assistant answer row.
- Each new prompt appends one user row and one pending assistant row keyed by `requestId`. Replace that pending row in place when the run completes.
- Follow-up prompts always create new runs in the same visible thread. Do not mutate prior answer cards and do not auto-inject hidden prior-run context.
- Use the existing friendly run-status language from `formatRunStatusLabel(...)` and the existing badge tone map for `success`, `partial_success`, `no_data`, `error`, `queued`, and `running`.
- Use `formatDate(...)`-style locale timestamps in the run strip. Prefer `finished_at` for terminal runs; fall back to `created_at` when a final timestamp does not exist.
- Keep any background-delivery note as muted supporting text below the structured card. It is supporting context, not the primary answer.
- Preserve the existing scope editor and composer placement. Phase 14 changes the answer contract, not the page layout or workspace navigation.

## State Contract

| State | Visual Contract | Copy Contract |
|-------|-----------------|---------------|
| Pending | Structured assistant card with muted surface or skeleton bars; same width and padding as the final card | `Running analysis...` with `Updating…` microcopy |
| Success | Compact answer card with conclusion first, goal second, run strip last | Use derived answer content; CTA label stays `Open run` |
| Partial / no data | Same compact answer card, but preserve orange or violet status badge and any conclusion rider | Keep the derived summary or fallback summary; do not add Phase 15 confidence strips |
| Error | Same compact answer card, but preserve red status badge and error-oriented summary copy | `This analysis didn’t finish cleanly.` followed by `Open run` |
| Unsupported routing | Existing prose guidance panel with rewrite suggestions only | Keep `I couldn't route that request yet.` and `Try one of these rewrites` |

---

## Phase Boundaries

- Do not render top findings, caveat badges, confidence strips, or evidence summaries in chat during Phase 14.
- Do not add `Deep dive`, `All runs`, or multi-link action rails to the assistant answer card.
- Do not introduce fully persisted multi-conversation chat threads.
- Do not inject prior answer context into later prompts without explicit user action.
- Do not redesign the standalone run page here; it remains the secondary verification surface until later phases.
